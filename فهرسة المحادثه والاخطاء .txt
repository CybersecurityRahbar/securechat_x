## 1. أخطر مشكلة: التشفير الحالي ليس Double Ratchet صحيحًا

يوجد `DoubleRatchetService`، لكن طريقة بناء الجلسة الحالية فيها مشاكل جوهرية.

مثلًا:

```dart
final dh1 = await _x25519Service.computeSharedSecret(
    ourIdentity, theirSignedPreKey);
```

ثم:

```dart
final dh2 = await _x25519Service.computeSharedSecret(
    ourSignedPreKey, theirIdentity);
```

وهكذا.

المشكلة ليست مجرد أسماء المتغيرات؛ **X3DH الحقيقي يحتاج protocol transcript واضح، اتجاهات صحيحة للمفاتيح، signatures للـ signed prekey، one-time prekey consumption، وربط الهوية والـ ephemeral key بالـ transcript**.

والأخطر أن `ensureInitialized()` يقوم بإنشاء مفاتيح للطرف الآخر محليًا:

```dart
final theirIdentity = await _x25519Service.generateKeyPair();
final theirSignedPreKey = await _x25519Service.generateKeyPair();
final theirOneTimePreKey = await _x25519Service.generateKeyPair();
```

هذا ليس handshake مع الطرف الآخر.

بل هو إنشاء **مفاتيح وهمية محلية للطرف الآخر**.

وهذا وحده كافٍ لأقول إننا لا ينبغي أن نعتبر النظام الحالي E2EE حقيقيًا.

# 3. هناك تناقض بين WebSocket encryption و Double Ratchet

`SecureWebSocket.sendMessage()` يقوم بـ:

1. JSON
2. gzip
3. AES-GCM
4. إرسال binary

لكن مفتاح AES هو:

```dart
_sessionKey
```

بينما الرسائل نفسها يفترض أن تستخدم:

```text
X3DH → Double Ratchet → Message Key → AES-GCM
```

إذن لدينا **طبقة تشفير ثانية** حول الرسالة.

هذا ليس خطأ بحد ذاته لو صممناه عمدًا كـ transport envelope، لكن المشروع الحالي لا يفصل بين:

```text
Transport encryption
Message E2EE
Identity authentication
Session establishment
```

وبالتالي يصعب جدًا إثبات صحة النظام.

لكن `selected` لا يتم تخزينه.

```dart
final randomWords = List<String>.from(words)..shuffle();
```

مرة أخرى.

```dart
if (!originalWords.contains(word))
```

ولا يتحقق من:

* اختبار ما إذا كان التنفيذ فعلًا مطابقًا للمواصفات.

خصوصًا أن مشروعنا ليس مجرد تطبيق Flutter عادي؛ لدينا أجزاء حساسة جدًا مثل cryptography وkey management، ولذلك **لا ينبغي أن نترك Codex يخترع architecture أثناء كتابة الكود**.

### Codex = المهندس الذي ينفذ داخل المستودع

وهنا يصبح Codex أفضل بكثير.

Codex مصمم أصلًا للعمل مباشرة على repository، وقراءة الملفات وتعديلها وتشغيل الاختبارات والـ lint/build، ويمكنه تنفيذ refactors كبيرة ومهام طويلة. ([OpenAI][1])

والأفضل أن نضع في المستودع ملفًا مثل:

```text
AGENTS.md
```

يحتوي على قواعد المشروع التي يجب ألا يخالفها Codex. OpenAI نفسها توصي باستخدام `AGENTS.md` لتحديد طريقة التعامل مع codebase والأوامر والاختبارات والمعايير. ([OpenAI][2])

**لذلك لن أقول لك: اذهب إلى Codex ودعه يعيد بناء المشروع كيفما يشاء.**

بل:

```text
أنا هنا
   ↓
نضع Architecture + Specification
   ↓
نكتب مواصفات دقيقة لكل مرحلة
   ↓
Codex ينفذ المرحلة داخل GitHub
   ↓
Codex يشغل tests/build/analyzer
   ↓
نراجع النتيجة هنا
   ↓
نصحح التصميم إن لزم
   ↓
المرحلة التالية
```

وهذا في رأيي **أسرع وأكثر أمانًا بكثير** من محاولة كتابة 300 ألف سطر دفعة واحدة.

بل حتى إرشادات OpenAI الخاصة بـ Codex توصي في المشاريع الكبيرة بالبدء بطلب خطة في Ask Mode ثم الانتقال إلى Code Mode، وتقسيم العمل إلى مهام محددة وقابلة للاختبار. ([OpenAI CDN][3])

# 4. والأهم: لا نكتفي بـ X3DH + Double Ratchet

```text

       ├── Device Identity
       ├── Signed PreKey
       ├── One-Time PreKeys
       └── Session Keys
```

مثلاً:

```text
You
 ├── Phone
 │    ├── Alice session
 │    └── Bob session

 └── Tablet
      ├── Alice session
      └── Bob session
```

وليس:

```text
user → global session
```

```text
      ↓

      ↓
```

> **SecureChat X uses a documented cryptographic architecture built from established, peer-reviewed primitives, with strict key separation, authenticated sessions, forward secrecy, post-compromise recovery, secure local key storage, and independently testable protocol components.**

## Phase 0 Audit Report — SecureChat X 2.0

**Phase discipline observed:** I made **no repository changes**. The working tree already contains an untracked generated directory, **`android/.gradle/`**; it was not created or modified by this audit. The existing prototype does not meet the SecureChat X 2.0 specification’s architecture, security, or test requirements and must not be treated as a production-secure foundation. 

### 1. Current architecture

- The application is a **single 10,773-line ****`lib/main.dart`**** monolith** combining app bootstrap, configuration, models, Hive adapters, cryptography, ratchet/session logic, persistence, networking, use cases, local storage, calls, notifications, Security Center, routing, theming, and every UI screen.
- Riverpod and GoRouter are present, but their boundary value is undermined because notifiers, use cases, platform APIs, database calls, crypto, and WebSocket traffic are all defined and frequently instantiated directly from UI code.
- There is no **`app/`**, **`core/`**, **`data/`**, **`domain/`**, **`features/`**, or **`services/`** layout. This directly conflicts with the target architecture defined by the specification. 

### 2. Complete repository/file map

- **Root:** **`AGENTS.md`**, **`README.md`**, **`pubspec.yaml`**, **`analysis_options.yaml`**, **`.metadata`**, and **`codemagic.yaml`**.
- **Documentation:** authoritative master specification and implementation roadmap under **`docs/`**.
- **Flutter/Dart:** only **`lib/main.dart`**; no package-level feature folders.
- **Tests:** no **`test/`** or **`integration_test/`** directories exist.
- **Android:** conventional Gradle wrapper/project files; one Kotlin **`MainActivity`**, manifest, launch styles, launcher icons, and generated plugin registrant.
- **iOS and web:** standard Flutter template scaffolding, assets, and generated/platform configuration. They are not within the Android-first Phase 0 implementation scope but remain tracked.
- **Assets:** there is no project-level **`assets/`** directory and therefore no declared assets in **`pubspec.yaml`**; Android/iOS/web icons are template assets.
- **Generated/local state:** **`android/.gradle/`** is untracked, and the repository has **no ****`.gitignore`**, creating an immediate risk that generated caches and local files will be committed accidentally. 

### 3. Current `main.dart` architecture

- **`main()`** initializes Hive, registers hand-written adapters, loads/creates a Hive key, runs Hive migrations, invokes superficial device checks, configures notifications, and starts the application. It catches startup errors and only logs them; it does not present a safe startup-failure state. 
- It is not a small entry point as required. Its configuration includes legacy infrastructure defaults in the same source file, and it owns both process initialization and much of the application’s architecture. 
- Routes span onboarding, recovery, biometric unlock, home, chat, search, contacts, profile, settings, Security Center, groups, and calls, but feature completeness is uneven and many surfaced claims are unsupported. 

### 4. Current dependencies

- Declared dependencies include crypto-related packages (**`cryptography`**, **`pointycastle`**, **`crypto`**, **`bip39`**), storage (**`flutter_secure_storage`**, **`hive`**, **`hive_flutter`**), transport/media (**`web_socket_channel`**, **`http`**, **`flutter_webrtc`**, **`record`**, **`audioplayers`**), UI/state/navigation, files/images, notifications, biometric authentication, and utility packages. 
- **Dependency review has not been documented** for maturity, license, Android support, security posture, transitive impact, or necessity, despite this being required for all added packages and especially crypto packages. 
- **`cross_file`** is imported directly but is not a declared direct dependency; it is currently reached transitively. Direct imports should always be declared explicitly in the future dependency review.
- Several declared packages appear unused in **`main.dart`**, including **`url_launcher`** and **`flutter_cache_manager`**; **`hive_generator`**/**`build_runner`** are present even though all Hive adapters are hand-written. This is unnecessary attack surface and maintenance work until justified.
- Version constraints are broad and no lockfile is committed, so reproducible dependency resolution is absent.

### 5. What can be reused

- **Product documentation:** the master specification and roadmap are the most valuable reusable assets and must remain the source of truth. 
- **Platform foundation:** the standard Android Gradle wrapper, Java 17 compilation setting, AndroidX configuration, Flutter embedding, launcher setup, and Kotlin activity can be retained after Android hardening and namespace/signing cleanup. 
- **Conceptual candidates only, not code reuse by default:** Ed25519/X25519 intent, AEAD intent, provider-based state management, GoRouter, localized English/Arabic support, local notifications, attachment selection, and WebRTC package evaluation can inform a rebuild. Their current implementations need independent validation or replacement.
- **UI inventory:** existing screens provide a list of desired product areas, but do not meet the Phase 2 design-system quality bar and should not dictate the target experience.

### 6. What should be refactored

- Android configuration, CI configuration, README, lint policy, app configuration, bootstrap wiring, routing, theming, localization, and screen inventory should be retained only after being separated into dedicated modules.
- Public data concepts—users, contacts, messages, settings, groups, attachments—should be redesigned into immutable domain entities and database records rather than retaining the current Hive-centric entities.
- Notification, file/media, connectivity, and call functionality should become ports/adapters behind domain interfaces, not UI-accessible singleton services.
- The current “use case” labels may guide naming, but the classes are not clean use cases because they depend directly on UI-oriented notifiers and infrastructure singletons. 

### 7. What must be completely rewritten

- **Cryptographic protocol and session management:** current X3DH/Double Ratchet code is not a safe or correct implementation.
- **Identity, device, prekey, recovery, key rotation, and verification systems.**
- **Persistence:** replace monolithic Hive with a layered relational database plus secure-storage integration, migrations, transactions, indexes, and protected session state.
- **WebSocket protocol/client:** define a client-first, versioned contract before the new server is built.
- **Messaging engine, offline synchronization, attachments, groups, calls, Security Center, settings, and UI design system.**
- **Tests and threat-model artifacts:** there are currently none.

Remove only in a later reviewed migration—not during Phase 0:

- The custom protocol code and security claims that call it “Double Ratchet,” “E2EE,” or equivalent before a reviewed established protocol implementation exists.

## Security and implementation findings

### 10. Cryptographic/security defects

1. **Critical — custom and incorrect protocol implementation.** **`DoubleRatchetService`** combines values that are not a valid authenticated X3DH transcript, does not verify a signed prekey, does not bind identities or a transcript, has no protocol version/downgrade protection, and misuses one-time prekeys. It treats X25519 private values as identity material in places where public/private roles and signing identities must be explicitly separated. 
   **Correct direction:** select and review a mature implementation/construction; document algorithms, roles, transcript, associated data, versioning, reset behavior, and test vectors before implementing Phase 5.
2. **Critical — unsafe fallback session creation.** **`ensureInitialized()`** generates both local and “their” key material on one device, then calls it a usable ratchet session. That cannot establish a session with another party and creates a false encryption guarantee. 
   **Correct direction:** never silently synthesize a remote session. Block sending with a typed “session establishment required/failed” state until an authenticated prekey bundle is obtained and verified.
3. **Critical — ratchet does not implement Double Ratchet behavior.** Envelopes contain only nonce+ciphertext; no ratchet public key, message number, previous-chain length, session ID, header authentication, skipped-key use, replay tracking, or DH ratchet execution is present. **`_skippedMessageKeys`** is never used. Incoming messages only advance the next chain key, so loss, reordering, duplication, and state divergence are not handled. 
   **Correct direction:** use a reviewed ratchet/session abstraction with atomic state persistence and tests for malformed, duplicate, replayed, skipped, reordered, reset, and recovery flows.
4. **High — AEAD metadata is not authenticated for messages.** **`ratchetSend`** calls AES-GCM without associated data, so conversation/session/message identity, sender/recipient, content type, ordering, and protocol version are not cryptographically bound to ciphertext. 
   **Correct direction:** require a versioned envelope and bind all security-relevant metadata as AAD, exactly as the specification requires. 
5. **Critical — session secrets can be written in plaintext.** **`saveState()`** writes root keys, chain keys, and DH private keys as JSON to an arbitrary file path. This violates the rule prohibiting plaintext session-secret storage. 
   **Correct direction:** remove this API in the replacement; persist sensitive ratchet state only through protected storage/database mechanisms with atomic transactions and retention controls.
6. **High — security audit integrity check is invalid.** It computes an HMAC using an all-zero key, compares **`Uint8List`** by object identity rather than constant-time byte equality, and is not integrated with actual inbound message verification. 
   **Correct direction:** do not expose a separate homemade integrity check; AEAD verification should authenticate the established envelope. Any comparison must be fixed-time where relevant and tested.
7. **High — backup encryption uses a fixed zero salt and an unsuitable password derivation.** A password is converted through custom HKDF with an all-zero salt, with no stored per-backup salt, no calibrated memory-hard password KDF, and no versioned backup format. 
   **Correct direction:** design backup/recovery in Phase 4/16 with a reviewed password-based encryption format, unique persisted salt/parameters, authenticated metadata, recovery policy, and negative tests. Do not improvise the KDF.
8. **High — security claims are false or unverifiable.** Onboarding promises Double Ratchet and perfect forward secrecy, while Security Center unconditionally reports encryption “Active,” identity “Verified,” and fingerprint “Match: 100%.” 
   **Correct direction:** remove unsupported claims in the future migration and show only observed, tested security state with remediation guidance.

### 11. Identity/key-management defects

- **Recovery is not recovery.** **`restoreIdentity()`** validates a mnemonic but ignores the derived seed, generates new Ed25519/X25519 key pairs, a new user ID, and placeholder “restored\_user” data. The restored identity cannot be the original identity. 
  **Correct direction:** decide and document the recovery hierarchy first. Recovery must restore the intended identity/device authorization state or explicitly establish a new identity with visible consequences—never label unrelated key generation as restoration.
- **Critical — recovery phrase is stored in encrypted Hive application data, then read directly from UI.** Encryption of the Hive box does not make storing seed/recovery material in ordinary app data acceptable; database key availability makes it recoverable by the application and backups serialize it indirectly through user-state workflows. 
  **Correct direction:** recovery material must never persist as normal database/preferences data. Define a verified, intentional recovery UX and secure lifecycle.
- The recovery verification screen shuffles words but does not retain or display requested positions; it therefore cannot validate exact requested positions as required. 
- The signed prekey has no Ed25519 signature, no expiration/rotation policy, and no proof binding it to the identity. One-time prekey **private keys are discarded immediately**, so private/public pairing, server consumption, and replay/duplicate use cannot be correct. 
- The prekey upload parameter accepts **`signedPreKeyPrivate`** but does not upload or otherwise use it, indicating confused API/key-lifecycle design. 
- Key rotation replaces identity keys without preserving device lifecycle, session reset, signed-prekey replacement, contact safety-number handling, verification migration, or revocation protocol. 
- **`clearKeys()`** invokes **`deleteAll()`**, deleting unrelated secure-storage entries such as database key, PIN, auth token, and flags rather than only the intended key namespace. 

### 12. Database defects

- Hive is a monolithic key-value database used from notifiers, UI, services, migrations, and use cases. It lacks the relational entities, indexes, query bounds, pagination, migrations, and repository boundaries required by the specification. 
- Message/contact/search paths enumerate whole boxes and filter in memory. This will not scale and violates the no-unbounded-routine-scan requirement. 
- **`createIndexes()`** merely re-saves every message and creates no index. 
- Migrations scan all messages, lack transactions/backup/rollback semantics, and contain an impossible **`DateTime is String`** type check, so migration correctness is not credible. 
- The offline queue attempts to persist a custom **`QueuedMessage`** without a registered Hive adapter, producing likely runtime serialization failure. 
- Session state is stored as JSON in a general Hive box instead of a typed protected session repository with atomic update behavior. 
- Backup/restore clears live boxes sequentially without validation, transactionality, identity/private-key restoration, session/prekey data, attachment metadata, or rollback. 

### 13. Messaging defects

- Outgoing plaintext is stored in **`MessageEntity.content`** before transmission and the architecture has no explicit encrypted-at-rest plaintext policy beyond box encryption. More importantly, session state is advanced before durable atomic persistence/transport reconciliation. 
- The send path does not queue when disconnected; it simply keeps a locally created message with no durable transition to a synchronization queue. The separate queue is not consistently wired into sending. 
- Statuses are opaque integers and do not model the required lifecycle (**`CREATED`**, **`ENCRYPTED`**, **`QUEUED`**, **`SENT`**, **`SERVER_ACK`**, **`DELIVERED`**, **`READ`**, **`FAILED`**, etc.). 
- Edit/delete/reply/read/typing events are plaintext JSON application fields sent through a non-authoritative transport protocol, without signed/versioned semantics or authorization/conflict handling.
- Incoming decryption fetches the alleged sender’s prekeys at receive time and uses their private fields incorrectly; it does not validate sender identity, message header, prekey consumption, replay, or session relationship. 
- Disappearing-message controls exist in a model but no reliable expiration scheduler, deletion policy, notification/cache treatment, or remote lifecycle exists.

### 14. WebSocket/network defects

- The default endpoint is a hard-coded ngrok development URL in production source, contrary to the configuration rule. 
- Socket authentication sends unauthenticated **`userId`**/**`deviceId`**; a server-provided symmetric **`sessionKey`** is accepted from an **`auth_response`** with no authenticated key exchange, certificate/pin enforcement, token binding, or device credential proof. This enables server or active-network substitution of the transport key. 
- Transport AES-GCM is custom-framed, has no schema/version/event ID/correlation ID/AAD, and must never be confused with message E2EE. Compression before encryption also requires explicit size/resource bounds to resist decompression abuse. 
- **`SecureWebSocket.connect()`** marks the socket connected before server authentication succeeds; reconnect dereferences nullable user/device IDs and has no cancellation token, jitter, maximum total duration, protocol negotiation, or durable reconnect/reconciliation semantics. 
- Certificate pinning is not applied to **`http`** or WebSocket requests. Its **`badCertificateCallback`** only runs for otherwise invalid certificates; it neither validates normal-certificate pins nor constrains hostnames, and returns **`false`** when no pin exists. 
- REST prekey, upload, and media-download calls are raw HTTP client calls with no consistent authentication, pinning, timeout, typed failures, content validation, or protocol version. 

### 15. Voice/video call defects

- The call manager creates peer connections and media streams but has no implemented signaling integration for SDP or ICE candidate exchange. ICE candidates are merely logged. 
- It relies on public Google STUN servers and supplies no TURN strategy, authenticated signaling, call/session authorization, identity verification, device selection, or formal call state machine. 
- The UI claim of perfect forward secrecy is unsupported. WebRTC media encryption is not a replacement for authenticated call signaling or contact identity verification. 
- Incoming-call handling, background execution, foreground-service behavior, notification action handling, reconnection lifecycle, missed-call history, audio routing, permissions, and call diagnostics are incomplete or absent.

### 16. Group/community defects

- **Critical — groups rely on a single randomly generated ****`groupSharedSecret`****, stored directly in the group entity.** There is no documented membership-change rekey protocol, key distribution, authorization, per-sender state, revocation, or encrypted group message implementation. 
  **Correct direction:** choose/document a mature group-encryption approach in Phase 10. Member removal must produce a verifiable rekey operation; do not use a casually persisted static secret.
- Group roles are only **`members`** and **`admins`**; permissions, invitations, verification, admin audit events, media policy, disappearing-message policy, and membership-change handling are absent.
- The public community feature is entirely absent. It needs a deliberately separate non-E2EE model, first-run invitation/reminder rules, moderation/reporting, mute/leave controls, and a clear UI distinction from private conversations. 

### 17. Settings/privacy defects

- Privacy booleans (**`hideOnline`**, **`hideLastSeen`**, **`hideReadReceipts`**, **`hideTypingStatus`**) are persisted but not consistently enforced in signaling or UI. This is a prohibited non-functional/fake-toggle pattern. 
- The settings screen explicitly leaves Privacy and Notifications navigation unimplemented. 
- Biometric setting persistence does not establish a complete application lock policy; the app lacks lifecycle lock-on-background/app-switch enforcement, failed-attempt policy, recents protection, screenshot protection, and sensitive clipboard controls.
- Notification APIs accept arbitrary plaintext title/body and use high-priority expanded text by default, risking lock-screen content exposure. There is no privacy mode matrix or per-conversation policy. 
- Export Logs writes an in-memory log buffer to the documents directory. Because logger callers interpolate unredacted exceptions and application data, this can exfiltrate sensitive metadata or content. 
- Backup UI permits sharing the backup file but lacks clear key/recovery/material scope, restoration warnings, secure deletion limitations, versioning, or integrity/recovery handling. 

### 18. UI/UX defects

- The interface is primarily generic Material cards, dialogs, list tiles, and a cyan seed color; there is no tokenized design system for typography, spacing, surfaces, radii, elevation, iconography, status colors, and motion. 
- The visual/security state frequently claims success by default rather than reflecting actual state, which is a UX and security defect. 
- Screen-level widgets carry storage, networking, crypto/session, backup, and WebRTC behavior directly, violating separation of responsibilities. 
- Loading, error, empty, offline, permission-denied, crypto/session-failed, and recovery-failed states are inconsistent. Some failures only produce logs or snackbars; several actions are no-ops.
- Reduced-motion support, responsive/tablet navigation, semantic/accessibility review, and complete localization resources are missing.

### 19. Android/build defects

- The Android app uses placeholder company namespace/application ID (**`com.yourcompany.securechat_x`**) and includes a comment instructing manual replacement. 
- **High — ****`usesCleartextTraffic="true"`**** is enabled** without a documented development-only network-security configuration. This weakens transport policy for a security product. 
  **Correct direction:** disable cleartext by default and use an explicitly scoped development configuration only if genuinely required.
- **`requestLegacyExternalStorage="true"`** and broad legacy external-storage permissions are inappropriate for a modern privacy-first app. Use scoped storage and the least permissions necessary. 
- Release builds explicitly use the debug signing configuration. This blocks a safe release process and must be replaced by protected release signing/CI secret handling before releases. 
- **`targetSdk`** is 34 while **`compileSdk`** is 35; upgrade policy has not been assessed. Permission declarations lack a complete media/call/foreground-service strategy.
- Gradle configuration contains Kotlin version inconsistency: root buildscript declares 1.9.22 while plugin management declares Kotlin Android 2.0.0. 
- **`codemagic.yaml`** supplies placeholders for server, certificate pin, credentials group, and email recipient; it lacks analyzer/test stages, dependency lock discipline, signing verification, secret scanning, and artifact provenance. 

### 20. Testing gaps

- No test or integration-test source tree exists.
- No unit tests cover crypto wrappers, identity recovery, session establishment, ratchet state, malformed data, replay, duplicates, out-of-order messages, key changes, database migration, backups, attachments, queueing, notification privacy, calls, or settings.
- No protocol document, fixture/test vectors, threat-specific tests, test database strategy, accessibility tests, or release-build validation pipeline exists.
- This fails the explicit testing requirements in the master specification. 

### 21. Security/threat-model gaps

No repository threat model exists. The Phase 0 threat model must specifically define assumptions, mitigations, and residual risk for:

- malicious/compromised relay and server database;
- network observer, MITM, certificate/key substitution, replay, downgrade, and reordering;
- stolen/rooted/debugged device and local database extraction;
- malicious contact, identity/device change, compromised remote device, and unauthorized linked-device actions;
- backup compromise, recovery-phrase disclosure, notification/clipboard/recents/screenshot leakage;
- attachment tampering, parser/malware risk, malicious file sizes, cache exposure, and transfer resumption;
- group membership changes and removed-member access;
- call signaling compromise, STUN/TURN metadata leakage, and media reconnection;
- metadata minimization, retention, diagnostics, and support/telemetry policy.

### 23. Proposed target folder structure

- **`app/`**: **`main_bootstrap.dart`**, **`securechat_app.dart`**, **`router.dart`**, **`app_scope.dart`**, **`environment.dart`**.

- **`domain/`**: immutable entities and repository/use-case contracts without Flutter/Hive/WebSocket types.

- **`services/`**: platform/transport adapters behind interfaces.
- **`test/`**** and ****`integration_test/`**: mirrored unit/database/protocol/UI/integration coverage from Phase 1 onward.

### 24. Migration strategy

1. **Preserve the legacy prototype in Git history**; do not copy its cryptographic protocol forward.
2. **Phase 1:** establish folder boundaries, typed errors, configuration, dependency composition, testing skeleton, and an isolated **`legacy/`** compatibility boundary if startup preservation is necessary.
3. **Phase 2:** introduce tokens, app shell, accessible navigation, and honest UI states; do not surface security claims that lack implementation.
4. **Phase 3:** build and migrate to a relational data model. Define an explicit legacy-data policy: import only non-secret, validated data where feasible; do not automatically migrate recovery phrases, static group secrets, or ratchet/session secrets.
5. **Phase 4–6:** design/review identity/recovery, then prekeys/crypto/session management with protocol documentation and test vectors before any real secure messaging claim.
6. **Phase 7–16:** build messaging, sync, verification, groups, community, attachments, voice, calls, Security Center, and settings only on those boundaries.
7. **Phase 17–21:** harden, freeze the client protocol, then build the compatible server and perform integration/release security review. 

### 25. Phase 1 implementation plan

1. Create the target folder skeleton and package conventions; add a root **`.gitignore`** that excludes Gradle/Dart/build/local-secret artifacts.
2. Reduce **`main.dart`** to bootstrap/composition only while retaining legacy startup behavior behind an explicit isolated boundary.
3. Introduce immutable app configuration with environment-specific validation; remove production/development endpoint decisions from widgets.
4. Introduce typed domain failures and redacted diagnostic/logging policy; disable raw log export as a security feature pending a safe diagnostics design.
5. Define repository interfaces and placeholder/in-memory adapters only where needed to preserve Phase 1 startup—not crypto/database/network features.
6. Establish test directories, test helpers, and CI checks for formatting, analysis, unit tests, and Android release build.
7. Create architecture decision records for dependency review, database selection, secure storage, and protocol-selection process.
8. Add an initial threat-model document and a legacy migration/risk register.
9. Do **not** implement real identity, recovery, crypto, sessions, network protocol, messaging, groups, media, or calls until their scheduled phases.

Summary
Replaced the 10,773-line legacy main.dart monolith with a minimal bootstrap entry point and introduced an application bootstrap that resolves non-secret environment configuration, installs a safe global error UI, and composes the root application scope. 

Created the layered Phase 1 architecture under app, core, data, domain, features, and services, including explicit contracts for future crypto, storage, database transactions/pagination, repositories, transport, WebSocket, connectivity, and lifecycle work. These are interfaces only—no fake cryptographic, database, transport, or persistence implementation is claimed. 

Added typed failures for network, crypto, database, protocol, authentication, permission, storage, configuration, validation, session, media, call, and unknown errors, plus a presenter that maps unexpected errors to redacted user-safe text. 

Built a functional application shell with routed Home, Chats, Contacts, Calls, Security, and Settings destinations; a lifecycle service; stock localization delegates; and a dark-first semantic theme. Unimplemented product capabilities explicitly state that they are unavailable rather than claiming encryption, verification, messaging, or calling. 

Established UI-system tokens and reusable foundation components for color, spacing, radii, motion, icons, cards, buttons, text fields, dialogs, bottom sheets, loading/error/empty states, and truthful security-status indicators. 

Removed the legacy runtime dependency set—including unreviewed crypto, Hive, networking, WebRTC, media, and state/router packages—and retained only Flutter SDK dependencies required by the Phase 1 shell. The reasoning is documented in ADR 0002. 

Hardened the Android baseline: changed the namespace/application ID to com.securechatx.app, moved MainActivity to the matching package, disabled cleartext traffic, removed legacy external-storage and premature feature permissions, and removed debug signing from the release build type.

Added unit/widget/integration test infrastructure covering environment validation, typed-error presentation, security defaults, application scope, lifecycle transitions, bounded pagination defaults, routed shell navigation, and application rendering.

# SecureChat X 2.0 — AGENTS.md

This repository is being rebuilt as SecureChat X 2.0. The authoritative product and architecture specification is:

`docs/SECURECHAT_X_2.0_MASTER_SPECIFICATION.md`

Read that document before making architectural or feature changes.

## 1. Mission

Build a production-quality Flutter/Android secure communications client first. The future server will be rebuilt to match the final client protocol. Do not allow the current broken server or current monolithic implementation to dictate the new architecture.

## 2. Non-negotiable rules

1. Do not invent cryptographic algorithms or proprietary security protocols.
2. Do not weaken security merely to make a feature work.
3. Do not claim a security feature exists unless it is actually implemented and tested.
4. Never store private keys, recovery phrases or session secrets in ordinary preferences or plaintext files.
5. Never log plaintext messages, private keys, recovery phrases, session keys, decrypted attachments or authentication secrets.
6. Never put business logic, crypto, database or network protocol logic directly into UI widgets.
7. `main.dart` must remain a small entry point after the migration; the old monolithic file is legacy code to be decomposed.
8. Never create settings toggles that do nothing.
9. Never hard-code production infrastructure into UI components.
10. Do not silently trust changed identities or devices.
11. Do not treat transport encryption as equivalent to end-to-end encryption.
12. Do not use a single static shared secret as a substitute for a documented group-encryption protocol.
13. Do not implement fake post-quantum, zero-knowledge or military-grade claims.
14. Do not add dependencies without reviewing maintenance, platform support and security implications.
15. Prefer established, mature cryptographic libraries and protocol constructions.
16. Every security-sensitive change requires tests.
17. Every feature requires error, loading and empty states where applicable.
18. Preserve protocol versioning and migration paths.
19. Keep UI, domain, data, crypto, network and platform responsibilities separated.
20. Do not delete existing functionality until its replacement and migration path are understood.

## 3. Workflow

Before a large change:

1. Read the master specification.
2. Inspect the relevant existing files and dependencies.
3. Explain the intended architecture/change in the task response.
4. Implement in small, reviewable units.
5. Run formatter/analyzer/tests appropriate to the changed area.
6. Run a release build for major milestones.
7. Report what changed, what was tested and any remaining limitations.

Do not make broad speculative rewrites without a clear phase/task boundary.

## 4. Current project strategy

The existing application is a legacy prototype. It contains useful ideas and code but must not be assumed correct. In particular, crypto, recovery, prekeys, session establishment, database access, WebSocket behavior, WebRTC signalling and settings must be independently validated before reuse.

Do not preserve an existing implementation merely because it already exists. Preserve it only if it satisfies the new architecture and security requirements.

## 5. Cryptography rules

- Treat cryptography as a separate subsystem.
- Use documented primitives and mature implementations.
- Separate identity keys, device keys, signing keys, prekeys, session state and message keys.
- Document key ownership and lifecycle.
- Use authenticated encryption for encrypted message/attachment payloads.
- Bind important protocol context through authenticated data where appropriate.
- Test malformed input, replay, duplicate messages, out-of-order delivery, skipped messages, identity changes and session resets.
- Never print secret material while debugging.
- Do not create custom KDFs, signature schemes, ratchets or encryption modes.
- Future post-quantum support must be versioned and algorithm-agile; do not invent PQ primitives.

## 6. Identity and recovery

Identity recovery must restore the intended identity or use an explicitly documented recovery hierarchy. It must never generate a new unrelated identity and call it recovery.

Signed prekeys must actually be authenticated by the identity/signing mechanism selected by the protocol. One-time prekeys require correct private/public lifecycle management and consumption tracking.

## 7. Database rules

- Use repositories/domain boundaries.
- Prefer indexed relational storage for large message datasets.
- Use migrations rather than destructive schema changes.
- Avoid unbounded scans on routine UI paths.
- Use pagination.
- Keep cryptographic session state protected.
- Never store plaintext recovery secrets.

## 8. Network rules

The future WebSocket protocol will be versioned and designed from the client first.

Separate:
- transport security
- authentication
- message E2EE
- session establishment
- synchronization
- delivery/read events
- presence
- call signalling
- attachment signalling

The server must not be treated as a source of message plaintext or private keys.

## 9. UI/UX rules

The UI must be premium, modern, professional and intelligence-oriented. Avoid generic messenger layouts, fake hacker terminals, excessive neon, arbitrary gradients and superficial military decoration.

Use a coherent design system with tokens for typography, spacing, surfaces, colors, radii, elevation, icons and motion.

Animations must communicate state and remain performant. Support reduced motion and accessibility.

Every screen needs intentional loading, empty and error states where applicable.

## 10. Security Center

Treat Security Center as a first-class feature, not a settings page. It must expose meaningful security state such as identity verification, device trust, session health, prekey health, database protection, recovery state and actionable security warnings.

## 11. Privacy

Minimize metadata and never add analytics that contain message plaintext or sensitive cryptographic material. Clearly document what is local and what requires server support.

## 12. Testing

At minimum, use:
- `flutter analyze`
- `flutter test`
- targeted integration tests
- release builds at milestone points

Security-sensitive modules require additional fixtures/test vectors and failure-mode tests.

Do not declare success because the project compiles. A feature is complete only when behavior, security, persistence, UX states and tests are complete.

## 13. Dependencies

Before adding a package, assess:
- maturity
- maintenance activity
- license
- Android support
- Flutter/Dart compatibility
- security relevance
- transitive dependency impact
- whether the package is actually necessary

For cryptographic dependencies, perform a deeper review and document why the selected library is appropriate.

## 14. Code quality

Prefer clear, explicit code over clever abstractions. Use strong typing, immutable models where practical, deterministic state transitions, dependency injection where useful, and small testable units.

Avoid:
- giant service classes
- global mutable state
- hidden side effects
- UI-driven database access
- UI-driven crypto operations
- duplicated protocol logic
- magic strings for security-critical message types

## 15. Git discipline

Keep changes reviewable. Use focused commits where practical. Do not commit generated build artifacts, secrets, credentials, keystores or local machine configuration.

Before major refactors, preserve the ability to understand or recover the old implementation through Git history rather than copying legacy code into the new architecture.

## 16. Phase discipline

Do not jump ahead casually. Work follows the master specification:

Phase 0 — specification/threat model
Phase 1 — repository restructuring
Phase 2 — design system/navigation
Phase 3 — secure storage/database
Phase 4 — identity/devices
Phase 5 — cryptographic protocol
Phase 6 — session manager
Phase 7 — messaging
Phase 8 — offline synchronization
Phase 9 — contacts/verification
Phase 10 — private groups
Phase 11 — public community
Phase 12 — media/files
Phase 13 — voice messages
Phase 14 — calls
Phase 15 — Security Center
Phase 16 — advanced settings
Phase 17 — hardening/testing
Phase 18 — client/server protocol freeze
Phase 19 — server implementation
Phase 20 — integration
Phase 21 — release security review

When a task belongs to a later phase, do not implement a shortcut that creates architectural debt in an earlier phase.

## 17. Definition of done

A task is complete only when:
- implementation is complete
- architecture boundaries are respected
- relevant UI states exist
- persistence works where required
- offline behavior is defined
- security implications are addressed
- tests exist and pass
- analyzer passes
- relevant integration checks pass
- no secrets are exposed
- documentation is updated where protocol/security behavior changed

For cryptographic work additionally require:
- protocol description
- threat assumptions
- key lifecycle
- test fixtures/vectors
- reset/failure behavior
- replay/out-of-order handling where applicable

## 18. First rebuild instruction

Before changing application behavior, perform a complete repository audit and produce a structured implementation plan. Do not rewrite `main.dart` blindly. Identify reusable code, obsolete code, security-critical defects, dependency issues, Android configuration issues, test gaps and migration risks. Then implement according to the current phase.

# SecureChat X 2.0 — Master Product, Security & Architecture Specification

**Status:** Authoritative design specification  
**Version:** 2.0  
**Implementation order:** Flutter/Android client first; compatible server second  
**Rule:** Security, correctness, privacy and maintainability take precedence over feature count.

## 1. Vision

SecureChat X 2.0 is a privacy-first secure communications platform with a premium intelligence-oriented interface. It is not a clone of an existing messenger. The client must be designed first as the authoritative product and protocol reference; the server will later be rebuilt to conform to the frozen client/server contract.

The product must support secure text messaging, voice messages, images, video, documents and arbitrary files; real-time voice/video calls; private groups; an optional built-in public community; multi-device identity; offline-first synchronization; advanced security/privacy controls; and a dedicated Security Center.

Security claims must be precise. The project must never claim absolute security or invent proprietary cryptography. Established, peer-reviewed primitives and mature implementations must be used.

## 2. Core principles

1. Security by design.
2. Zero-trust server model: the server is a relay/service and must not need message plaintext or client private keys.
3. Local-first behavior and encrypted local state.
4. Strict cryptographic key separation and lifecycle management.
5. Established cryptography only; no home-made algorithms or protocols.
6. Explicit identity, device and session verification.
7. Minimal metadata collection and retention.
8. Advanced controls without overwhelming ordinary users.
9. Accessibility, performance and reduced-motion support are mandatory.
10. Every security control must be real, tested and documented; no fake toggles.

## 3. Product areas

- Onboarding and Identity
- Home / Secure Command Center
- Conversations
- Contacts and Identity Verification
- Private Groups
- Public Community
- Calls
- Secure Media and Files
- Security Center
- Settings
- Notifications
- Devices and Sessions
- Backup and Recovery
- Network / Connection Center
- Diagnostics

## 4. Identity and devices

The first-run flow creates a cryptographic identity, registers a device, initializes secure storage, establishes recovery and applies secure defaults. Identity and device keys are separate concepts.

Required concepts:
- stable user identity identifier
- long-term identity key
- device identity key
- signing capability
- signed prekey
- one-time prekey pool
- secure private-key storage
- key rotation
- device revocation
- recovery lifecycle

Recovery must actually restore the intended identity or explicitly documented recovery hierarchy. Generating a new unrelated identity while calling it restoration is prohibited.

Every device gets its own cryptographic material and sessions. Devices can be independently verified and revoked.

## 5. Cryptographic architecture

The exact algorithms and libraries require a dedicated cryptographic review before implementation. The following is the target architecture, not permission to invent a new protocol.

### Identity

Use an established digital-signature identity mechanism. Clearly separate long-term identity, device identity, signing keys, prekeys and session keys.

### Asynchronous key establishment

Use an established authenticated asynchronous design comparable to X3DH, or a mature successor/hybrid construction. Requirements include authenticated identity binding, signed prekey, one-time prekeys, correct private/public pairing, transcript binding, replay resistance, session versioning and downgrade protection.

### Message sessions

Use a mature ratcheting construction comparable to Double Ratchet or a well-reviewed successor. Required behavior includes unique message keys, DH ratchet, symmetric chains, skipped-message handling, out-of-order delivery, replay detection, session reset, recovery and post-compromise recovery where supported.

### Message encryption

Use authenticated encryption with associated data (AEAD) from a mature implementation. The authenticated envelope must bind protocol version, sender/recipient context, conversation/session ID, message ID, relevant ordering information and content type as appropriate.

### Key hierarchy

```text
Root Identity
  └── Device Identity
       ├── Signed Prekey
       ├── One-Time Prekeys
       └── Session State
            ├── Sending Chain
            ├── Receiving Chain
            └── Message Keys
```

Keys must never be reused across unrelated purposes.

### Secure storage

Use platform secure storage and Android hardware-backed keystore capabilities when available. Minimize plaintext key lifetime in memory and never log secrets.

### Post-quantum readiness

The protocol must be versioned and algorithm-agile so a future mature hybrid classical/post-quantum key-establishment mechanism can be added. Do not implement home-made post-quantum cryptography.

## 6. Identity verification

Contacts have explicit security identities. Provide:
- fingerprint
- QR verification
- numeric/manual comparison
- verified/unverified state
- device trust
- identity-change warnings
- session reset
- revoke/block/quarantine

A change to a verified identity must produce a prominent warning and explain possible benign causes without silently trusting the new identity.

## 7. Local database

Replace the current monolithic Hive usage with a properly layered relational database architecture, preferably SQLite/Drift or another well-supported indexed solution after dependency review.

Suggested entities:
- users
- devices

- database tests
- serialization tests
- crypto wrapper tests
- protocol fixtures/test vectors
- malformed-input tests
- replay/duplicate tests
- skipped-message/out-of-order tests
- identity-change tests

- integration tests
- UI tests
- accessibility checks
- `flutter analyze`
- `flutter test`
- integration tests
- release build

Cryptographic features additionally require a documented protocol, threat model, fixtures/test vectors, key lifecycle and failure/reset tests.

## 30. Threat model

At minimum consider:
- malicious server
- compromised server database
- network observer
- stolen/lost device
- malicious contact
- compromised contact device
- replay attacker
- impersonation
- key substitution
- downgrade
- attachment tampering/malicious files
- notification leakage
- clipboard leakage
- screen capture
- local database extraction
- backup compromise
- multi-device compromise
- metadata leakage

For each threat document assumptions, security goal, mitigation and residual risk.

## 31. Secure defaults

Default posture:
- E2EE enabled
- conservative notification previews
- encrypted local sensitive state
- screen protection where supported
- conservative media auto-download
- security alerts enabled
- identity verification encouraged
- no plaintext diagnostics
- no analytics containing message content

## 32. Error handling and observability

Errors must be typed by network, authentication, crypto, database, permission, media, file, protocol, session, input and platform categories.

User-facing errors are understandable. Developer diagnostics are detailed but redacted.

Never log private keys, recovery phrases, session keys, message plaintext, decrypted attachments or authentication secrets.

## 33. Performance

Use pagination, lazy media loading, background/isolate work for CPU-heavy operations, efficient thumbnails, bounded memory, indexed queries and controlled reconnects. Never block the UI thread with expensive cryptographic or database operations.

     3	**Status:** Phase 1 foundation. This document records security posture, not completed protocol guarantees.
     4	
     5	| Threat | Current mitigation status | Notes and residual risk |
     6	| --- | --- | --- |
     7	| Malicious server / compromised server database | PLANNED | The client/server protocol and E2EE are deferred to Phases 5 and 18; a server can currently not be trusted with content or identity assertions. |
     8	| Network observer or MITM | IMPLEMENTED (baseline) | Android cleartext traffic is disabled. Authentication, certificate policy, and E2EE are NOT IMPLEMENTED. |
     9	| Identity substitution | NOT IMPLEMENTED | Identity lifecycle and explicit verification are Phase 4 and Phase 9 work. |
    10	| Replay and downgrade | NOT IMPLEMENTED | Versioning boundary exists; authenticated envelopes and replay defenses await Phase 5. |
    11	| Stolen device / rooted device | PLANNED | Secure storage, device integrity posture, lock policy, and recovery are not implemented. |
    12	| Compromised contact | NOT IMPLEMENTED | No contact or verification implementation exists. |
    13	| Backup compromise | NOT IMPLEMENTED | Backup and recovery are deferred; no recovery material is created or stored. |
    14	| Notification and clipboard leakage | PLANNED | No notification or clipboard feature is active. Privacy defaults will be implemented with those features. |
    15	| Attachment threats | NOT IMPLEMENTED | Attachments are not implemented. |
    16	| Group membership threats | NOT IMPLEMENTED | Groups are not implemented. |
    17	| Call signalling threats | NOT IMPLEMENTED | Calling/signalling are not implemented. |
    18	| Metadata leakage | PLANNED | No transport runs in the Phase 1 shell. Metadata minimization requires the future protocol. |
    19	
    20	## Current security controls
    21	
    22	- **IMPLEMENTED:** no endpoints, credentials, or security claims are embedded in UI; cleartext Android traffic is disabled; the error model separates user-safe text from developer diagnostics.
    23	- **PLANNED:** platform-secure secret storage, encrypted database, identity, authenticated key establishment, ratcheting, transport authentication, notification privacy, and screen protection.
    24	- **NOT IMPLEMENTED:** end-to-end encryption, identity verification, local encrypted database, recovery, messaging, calls, group security, and server protocol.
Phase 1 Foundation Rebuild Report
Summary
Replaced the 10,773-line legacy main.dart monolith with a minimal bootstrap entry point and introduced an application bootstrap that resolves non-secret environment configuration, installs a safe global error UI, and composes the root application scope.

Created the layered Phase 1 architecture under app, core, data, domain, features, and services, including explicit contracts for future crypto, storage, database transactions/pagination, repositories, transport, WebSocket, connectivity, and lifecycle work. These are interfaces only—no fake cryptographic, database, transport, or persistence implementation is claimed.

Added typed failures for network, crypto, database, protocol, authentication, permission, storage, configuration, validation, session, media, call, and unknown errors, plus a presenter that maps unexpected errors to redacted user-safe text.

Built a functional application shell with routed Home, Chats, Contacts, Calls, Security, and Settings destinations; a lifecycle service; stock localization delegates; and a dark-first semantic theme. Unimplemented product capabilities explicitly state that they are unavailable rather than claiming encryption, verification, messaging, or calling.

Established UI-system tokens and reusable foundation components for color, spacing, radii, motion, icons, cards, buttons, text fields, dialogs, bottom sheets, loading/error/empty states, and truthful security-status indicators.

Removed the legacy runtime dependency set—including unreviewed crypto, Hive, networking, WebRTC, media, and state/router packages—and retained only Flutter SDK dependencies required by the Phase 1 shell. The reasoning is documented in ADR 0002.

Hardened the Android baseline: changed the namespace/application ID to com.securechatx.app, moved MainActivity to the matching package, disabled cleartext traffic, removed legacy external-storage and premature feature permissions, and removed debug signing from the release build type.

Added Phase 1 threat-model, migration-risk, and architecture/dependency ADR documentation. These documents clearly distinguish IMPLEMENTED, PLANNED, and NOT IMPLEMENTED controls and explicitly defer protocol, identity, storage, and server guarantees.

Added unit/widget/integration test infrastructure covering environment validation, typed-error presentation, security defaults, application scope, lifecycle transitions, bounded pagination defaults, routed shell navigation, and application rendering.

Deleted the legacy Android activity package file and the monolithic legacy application architecture. The legacy remote endpoint, certificate pin configuration, Hive usage, crypto code, WebSocket/WebRTC implementation, and feature logic are no longer imported into the executable client foundation.
